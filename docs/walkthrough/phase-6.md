# Phase 6 — The console and the demo agent

Two clients, for two different readers. The console is for the operator who has to answer "what
happened to this payment". The demo agent is for the reviewer who has to answer "can an agent get
around the mandate".

## The console

`console/` is a Vite + TypeScript single page, no framework: four views over the operator API.

| View | What it shows |
|---|---|
| Overview | open payments, net captured, agents, unresolved discrepancies, and two live invariants: the ledger conserves, no balance is negative |
| Payments | every payment with its state and reason code; clicking one opens its event timeline and its ledger postings |
| Mandates | the mandate as uploaded, with `remainingTotal` computed from the spend counters |
| Audit | the hash chain's verdict and the entries themselves |

It talks to the gateway through Vite's development proxy, so the browser never needs CORS and the
admin token is sent as a header, never as a cookie. The token is entered by the operator and kept in
`sessionStorage`: baking one into a bundle would put a demo credential in every browser cache, and
pretending a static page can hold a secret is worse than asking for it.

Payments by state is not decoration: `CAPTURE_UNKNOWN` sitting in that table is the one state an
operator must not miss, because it is the state where nobody knows whether the money moved.

## The demo agent

`demo-agent/` is an MCP client written against the protocol (`initialize`, `tools/list`,
`tools/call`) with no vendor SDK. It runs one control case and seven abuse cases, and it prints
Markdown so the run is checkable evidence rather than a claim.

The control case is the important one: a legitimate payment, then **the same request again with the
same idempotency key**, which must return the same payment with `replayed: true`. A gateway that
creates a second payment here is a gateway that double-charges on a network retry.

## The bug the demo agent found

The first run of the abuse suite **passed a payment to a merchant outside the allowlist**.

The cause was in the product, not the test: a mandate may allow a *category*, and the gateway was
evaluating the category the agent sent in the request. Since an agent can type `groceries` for any
merchant, a category rule was unenforceable — the allowlist said "groceries" and the agent said
"this is groceries".

The fix is a merchant directory the operator controls (`V3__merchant_directory.sql`,
`MerchantRepository`, `POST /admin/merchants`). The gateway now resolves the merchant's category from
that table and passes only that to the policy engine; the agent's claim is kept as a hint on the
payment record and is not used for authorisation. An unknown merchant has no trusted category, so a
category-only rule cannot match it.

This is exactly the kind of defect an adversarial client is for. The integration tests could not
have found it: they all told the truth about what they were paying.

## Abuse results

From `docs/ABUSE-RESULTS.md`, generated by the run:

| Case | Outcome |
|---|---|
| amount above the per-transaction limit | `AMOUNT_OVER_TX_LIMIT` |
| merchant outside the allowlist | `MERCHANT_NOT_ALLOWED` |
| currency the mandate does not use | `CURRENCY_MISMATCH` |
| zero amount | `AMOUNT_NOT_POSITIVE` |
| mandate that does not exist for this agent | rejected, no payment created |
| idempotency key reused with a different amount | rejected as a conflict |
| another agent's mandate | rejected: "mandate was not issued to this agent" |

Every one of those decisions is made by the gateway. None of them is a prompt, a model instruction
or a client-side check.

## Honest gaps

- The console has no tests. Its correctness claim is "it compiles and it builds"; the API it calls is
  covered by the gateway's integration tests, and the rendering was checked by loading it, not by an
  automated test.
- It is read-mostly: the only mutation is "run reconciliation".
- The demo agent's abuse suite is a fixed set of seven cases against one mandate. It is a
  demonstration of enforcement, not a fuzzer.
- No screenshots or accessibility pass are claimed.
